# ノウハウのまとめ方

## 一つの記事で扱うこと

「何を作るときの話か」を先に書き、採用する初期値と、用途によって変える判断を分ける。
ツールの一覧で終わらせず、担当する役割、組み合わせ方、運用時の注意点まで残す。
特定のアプリ名、ディレクトリ、バージョンに依存する話は、例であることを明示する。

記事は `docs/<テーマ>.md` に置き、READMEからリンクする。
関連する記事を参照し、共通の説明をむやみに複製しない。

## 基本の流れ

1. **用途と前提**: 何を作るときに役立つか。
2. **まず採用するもの**: おすすめの組み合わせと理由。
3. **設定で押さえる点**: 何を揃え、何を個別に決めるか。
4. **導入・確認の順序**: 新しいリポジトリで何から進めるか。
5. **運用と更新**: 再現性、依存更新、失敗時の扱い。
6. **参考資料**: 公式情報、参考リポジトリ、確認日。

文章だけでは伝わりづらいところに、短い設定例やコマンド例を添える。
サンプル一式を作ることを記事の目的にしない。

## 情報を更新するとき

変化しやすい仕様は公式資料を確認し、記事に確認日を記す。
プレビュー機能や利用条件がある設定は、採用できる環境と代替手段も書く。
参考リポジトリはコミットを固定して読み、どの設計を一般化したかを説明する。

資料から分かることと、実際の利用先で確認すべきことを区別する。
この記事の例を採用する際は、プロジェクトの構成・権限・配布先に合わせて検証する。
