# ノウハウのまとめ方

記事は `docs/<テーマ>.md` に置き、READMEからリンクする。
設定・配置・実行順は、文章で列挙するより短いコード例を優先する。採用理由や適用条件は文章で残す。

## 記事の型

必要な節だけ使う。長い説明を先に書かず、対象ファイルと最小例を読めば始められる形にする。

````markdown
# <用途>の定番

<対象と、まず採用する構成を1〜2文で>

## 最小の設定

対象: <ファイルのパス>
前提: <ツールの版・環境・準備済みのもの>
置換: <名前・パスなど、利用先で変える値>

```text
ここに、その言語のコードフェンスで最小のコード・設定を書く。
```

## 確認する

<実行ディレクトリ、確認コマンド、成功条件>

## 変える条件・注意点

- <この構成を選ばない条件>
- <権限・互換性・失敗時の注意>

## 参考資料

確認日: YYYY-MM-DD。<実行して確認した範囲と未確認の範囲>
<公式資料のリンク。参照実装はcommitを固定>
````

## 例を残すときの確認

- そのまま使える例か、既存ファイルへ追記する断片かを明示する。省略箇所を動くコードに見せない。
- 設定名・API・コマンドは採用版の公式資料で確認する。必要な依存やツールの準備を省かない。
- 確認コマンドは実装・設定と対応させる。書いただけのコマンドを実行済みと報告しない。
- 共通例は一か所へ集め、関連記事から参照する。別repoへ転記するテンプレート内のリンクは公開URLにする。
- サンプル一式を実装することを目的にしない。判断に必要な例を残し、詳細な仕様は公式資料へリンクする。
- プレビューや環境依存の機能は、利用条件と代替手段を併記する。既存の安全条件を短縮で落とさない。
